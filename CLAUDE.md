# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`coop` is a tmux-native TUI for monitoring many Claude Code sessions at once: each `claude` runs in its own tmux session on a dedicated socket (`tmux -L coop`), and the TUI (living in a `roost` session on that socket) shows every session's status, previews the selected one live, and forwards keys to it.
## Commands

```bash
go build -o ~/.local/bin/coop ./cmd/coop   # build/install
go test ./...                              # unit tests
go test ./internal/tui -run TestName       # single test
scripts/e2e-smoke.sh                       # e2e on a throwaway tmux socket (needs tmux ≥ 3.2)
```

## Architecture

Five packages under a thin `cmd/coop/main.go`:

- **`internal/hub`** — everything tmux. The `Tmux` interface is the subset of the tmux CLI the app needs; `ExecTmux` shells out (`tmux -L <socket> …`), and unit tests substitute the fake in `internal/hub/fake_tmux_test.go`. Also holds status derivation, done-tracking, sort order, session naming, live-pane command strings, and the shared focus palette.
- **`internal/tui`** — the Bubble Tea model. One file, `model.go`.
- **`internal/config`** — `~/.config/coop/config.json`: `repos` for the new-session picker, `tmux` override commands, `arbiter.model` (defaults to sonnet). `AddRepo` is the one writer: it rewrites the file from its own raw JSON, key by key in source order, so settings coop does not model survive and existing `~/` entries stay unexpanded. It refuses to rewrite a file that does not parse.
- **`internal/toolbox`** — everything container: the `Engine` interface over the docker CLI, image resolution from an embedded base Dockerfile plus a repo's optional overlay, shim generation, and the run/exec argument construction. See the toolbox section below.
- **`internal/skills`** — the Claude Code plugin coop injects into the sessions it launches, carrying the one `/coop:init` skill. See the skill section below.

### Core design: tmux is the database

There is no daemon and no state file. The model is a `[]hub.Pane` rebuilt from scratch by a 1-second `tmux list-panes` poll; `Status` is derived fresh every poll (`DeriveStatuses`), never stored. Claude's own state lands in tmux too: every session coop launches runs with a `--settings` file coop wrote (`WriteSessionSettings` writes it, `WithHookSettings` appends the flag). The file is coop infrastructure, regenerated so it always names the running binary, and it registers `coop hook` on each event coop cares about. **Which** file is per session, not per hub: a session on a repo with a toolbox gets `$XDG_STATE_HOME/coop/toolbox/<slug>/settings.json`, carrying that repo's `Bash(<tool> *)` grants beside its shims (see the toolbox section); everything else gets the grant-free `$XDG_STATE_HOME/coop/hooks-settings.json`, written once at hub launch as before. That is why `launcher` (`cmd/coop/launch.go`) assembles a session's command at create time rather than the hub assembling one string at startup — and why the order in it is fixed: `--settings`, then `--plugin-dir`, then `--add-dir`, which is variadic and swallows any flag appended after it. `TestLauncherKeepsAddDirLast` exists because that failure is silent — the session starts, `--settings` is read as a directory, and the status tier and every grant vanish with nothing logged. Status then comes from two sources, in order:

1. **The session's hook-published state** (`internal/hub/hook.go`, `cmd/coop/hookcli.go`) — Claude Code runs `coop hook` with the event JSON on stdin, and `ApplyHook` writes it onto `$TMUX_PANE` as `@coop_claude_status` (`busy`/`waiting`/`idle`), `@coop_status_since`, `@coop_session_id` and `@coop_claude_cwd`; the poll reads them back through `paneFormat`, so a status costs no tmux traffic beyond the `list-panes` already running. `UserPromptSubmit`/`PostToolUse`/`PermissionDenied` mean busy, `PermissionRequest` and the needs-input `Notification` types mean waiting, `Stop` and `idle_prompt` mean idle, `SessionEnd` unsets the lot. `SessionStart` always refreshes id and cwd but only sets idle for `startup`/`resume`/`clear` — `compact` and `fork` fire mid-turn, where flipping a busy row idle would be a lie. The since option moves only when the status actually changes, so a busy→busy `PostToolUse` doesn't reset "working 5m" to zero. The whole path is silent and best-effort: `coop hook` always exits 0 and prints nothing but the toolbox session note below (stdout is parsed by Claude Code as JSON, stderr lands in the session's transcript), so a failure is one stale row until the next event, never a wedged session. This replaced reading Claude Code's undocumented `~/.claude/sessions/<pid>.json`, which no longer exists here — a contract Claude Code publishes beats a file shape observed on one version.
2. **The pane title** Claude Code sets (braille spinner = working, 🔔/bell = needs input). It is the only fallback, and the whole story for panes that publish nothing: sessions started outside coop, and anything launched under `-hooks=false` (`COOP_HOOKS=0`), the opt-out `scripts/e2e-smoke.sh` uses because its fake claude takes no flags — an accepted regression from the old capture fallback: an attached session never latches the bell, so a hook-less pane sitting on an open dialog now reads idle rather than waiting.

`StatusFor` lets the published state win, except in the two places the event stream has a gap and the title proves it stale: nothing fires between approving a tool run and its `PostToolUse`, so waiting + spinner means the dialog was already answered; and nothing fires on an esc-interrupt, so busy + bell means Claude has rung for input since. An unrecognized status string — one a later coop wrote — falls through to the title rather than mislabelling a pane.

The time column ages from `Pane.Since()` — `@coop_status_since` where there is one, else the session start — so a row reads "waiting 6m", not "session started 3h ago".

### The stat column (`internal/hub/transcript.go`)

`s` cycles an optional right-hand column: off → context → model. Off is the default, and the poll skips transcript I/O entirely while it is (`nil` stats func), so the nav keeps its pinned `navWidth`. Turning it on widens the pane to `navWidth+statWidth` via the same `resizeSelf` path a terminal resize uses.

`Transcripts` reads `~/.claude/projects/<slug>/<sessionId>.jsonl`, resolving the file from the `@coop_session_id` and `@coop_claude_cwd` the pane's hooks published (with a by-id glob fallback, since a session outlives a directory rename). Only the last `tailBytes` are read and only the last main-thread assistant turn is parsed — subagent turns (`isSidechain`) carry unrelated context. Results cache on mtime+size so a 1-second poll doesn't re-parse. Context is that turn's `input + cache_read + cache_creation`, so it lags by a turn; there is no published window limit (sessions run both 200k and 1M), so it renders as an absolute count, never a percentage. Anything missing renders blank, never `0k`.

The one status needing memory across polls — `done` (finished working, not yet seen) — is persisted as tmux **user options on the tracked panes themselves** (`@coop_working`, `@coop_done_since`, managed by `DoneTracker`), so multiple hub instances on the socket share one view and state dies with its pane. Other user options: `@coop` marks a hub instance's own session (hidden from the list, used to reuse detached hubs), `@coop_live` marks the live preview pane (so a restarted TUI adopts it instead of stacking splits), and the `@coop_arbiter_note|suggest` episode markers below. The arbiter's *mode* is the one piece of shared state that is not a pane's: it is a global option, because there is no arbiter session to hang it on and a judge process runs outside any hub. None of these is a security boundary — every process in a monitored pane inherits a `$TMUX` pointing at coop's socket, so anything on it is one already-approved tool call from being rewritten by a session coop is watching.

### The arbiter (`internal/hub/judge.go`, `internal/hub/arbiter.go`, `cmd/coop/judgecli.go`)

`a` toggles a triage judge: off ↔ recommend. There is no confirm, because there is nothing to kill — the mode is a socket-global tmux option (`@coop_arbiter_mode`, unset = off), so turning it off is an option write like any other, and every hub on the socket and every judge process sees the same value. There is no third mode: the arbiter cannot send a keystroke, so the only question the mode answers is whether it judges at all. `ArbiterMode` reads anything but an explicit `recommend` as off — unset, a read error, a value a future version writes, and the `full` an older coop left on a socket it shares: the mode that does nothing is the default, never the accident, and silently promoting a stale `full` to the judging mode would resurrect a setting by accident that was removed on purpose. The poll reads it with an explicit `show -gv` rather than through `paneFormat` — `#{@coop_arbiter_mode}` probably does resolve globally through the option hierarchy, but that is unverified on 3.4 and the explicit read costs one tmux call a tick.

There is no arbiter session and no arbiter row. Judging is one headless `claude` per needs-input episode: `coop hook` publishes `waiting` and then `spawnJudge` (`cmd/coop/hookcli.go`) starts a detached `coop judge <pane>`, gated on the mode and on `ClaimEpisode` — an `O_EXCL` file under `~/.local/state/coop/claims` keyed pane + `@coop_status_since`, because a tmux option cannot be tested and set in one step and two hook processes (a `PermissionRequest` and the `Notification` about it) race for one dialog. That path comes from `claimRoot`, not `stateDir`, and so is the one state path that ignores `$XDG_STATE_HOME`: `ClaimEpisode` runs inside `coop hook`, in the monitored pane, where that variable is the session's to set — and setting it does not even take code execution, since an `env` block in a repo's `.claude/settings.json` reaches claude's environment at startup. A session that varied it per event would land every claim in a fresh directory and get one judge per event for a single dialog, which is precisely what the `O_EXCL` create exists to stop. The claim is taken **last**, after every other failure path, and released when the spawn itself fails: a claim consumed by a judge that never ran would wedge that dialog for good, since the next hook event for it carries the same `since`. That `since` is unix seconds, so two episodes on one pane inside a single second share a key and the second is never judged — it fails safe, to a row that just reads "waiting". The child is `setsid`'d because Claude Code reaps the hook's process group the moment the hook returns, and the judge outlives it by a model turn. The event is the dedupe unit, so there is no leader election and no hub required: judging keeps working with every TUI detached.

`coop judge` captures the pane, resolves the last assistant message through `Transcripts`, and runs `claude -p --output-format json` with `arbiterPreamble` plus the user's `arbiter.md` as `--append-system-prompt`. Its cwd is the empty coop-owned `arbiter/` directory **on purpose**: `coop hook` runs with the monitored session's cwd, and `claude` loads a `CLAUDE.md` from its working directory, so inheriting it would pull the judged repo's instructions in through a door the preamble's untrusted-data framing does not cover. No `--settings` is passed and `TMUX_PANE` never reaches it — belt and braces against the judge's own hooks writing status onto the very pane it is judging; either alone works, and either alone is a single point of failure. `claude` is resolved against a **constructed** `PATH`, never the hub's `-claude-cmd`, whose interactive `--continue`/`--resume` would answer out of an unrelated conversation.

That capture is not a single shot. `captureDialog` retries until `NeedsInputScreen` says the dialog is on screen, because `PermissionRequest` fires **before** Claude Code renders one — a hook may decide the permission itself, so the paint waits for every hook to return, and the judge is spawned from that hook. Losing that race does not produce a stale row, it produces a wrong one: the model gets a real trigger beside a screen with no dialog on it and escalates with "no numbered dialog is visible on screen to confirm", which reads as a judgement about the command rather than about the capture. Each attempt is one `capture-pane` and the whole bound is a fraction of the model turn it precedes, so the wait costs nothing next to the call it protects. A screen that never grows a dialog is still judged — an escalation over a capture that genuinely showed none is the honest outcome, and the episode's `dialog=` line is what tells that apart from a verdict blaming the screen. Only an answered dialog is dropped: the human now has the whole wait to be faster in, so each attempt re-reads `@coop_claude_status` and treats *only* a status that positively says otherwise as the end of the episode. A failed read and an unset option are both "don't know", and reading either as an answer would abandon every episode after one attempt — the original race, restored. Note that `NeedsInputScreen` only inspects the last `screenTail` non-empty lines, so a dialog buried under a long todo list costs the full bound and then judges anyway; that is latency, never a wrong verdict, since the model is handed the whole screen either way.

The prompt (`buildJudgePrompt`) is the session name, the trigger, the screen, and the last assistant message — plus, when the payload carried one, the **subagent** that made the request. Claude Code's `agent_id`/`agent_type` common input fields are present on every hook fired inside a Task sidechain and on none fired on the main thread, so `HookAgent` reads their presence as the fact and `-agent` carries it from the hook to the judge. It matters because `Transcripts.LastText` deliberately skips `isSidechain` turns: for a subagent's dialog the "last assistant message" is the *parent's* narration ("dispatching review"), which unlabelled reads as an explanation of a request it has nothing to do with — the observed cost was an escalation of "unclear what 'dispatching review' entails" on a subagent's Bash prompt. The message is labelled rather than dropped (the main thread's plan is the context the subagent was dispatched under), and the fix stops at the payload: the transcript's JSONL shape is documented as internal and unstable, so hunting the sidechain's own turn there is not a second source worth having. `agent_type` is attacker-influenceable like every other payload field, so it goes through `sanitizeNote` and is rendered `%q` inside its heading — a name that could close the heading and open a forged instruction is a prompt-injection door.

`JudgeEnv` (`internal/hub/judgeexec.go`) is that construction, and it is an **allowlist**, applied at both hops out of the pane (the hook's spawn of the judge, and the judge's spawn of `claude`). A denylist was tried and cannot hold this shape: the environment a judge inherits is the monitored session's own, and the set of variables Claude Code honours grows with each release — `PATH` (which decides which binary *is* the judge), `CLAUDE_CONFIG_DIR`, `HOME`, `HTTPS_PROXY`/`NODE_EXTRA_CA_CERTS`, the Bedrock/Vertex switches. So only `LANG`/`LC_*`/`TZ`/`TMUX_TMPDIR` pass through, `HOME` comes from the password database rather than `$HOME`, and `PATH` is built from coop's own executable directory, `~/.local/bin` and the system directories. `XDG_STATE_HOME` is deliberately *not* passed on: it resolves the judge's audit log and judge log, and a redirected audit is a silenced record. Between that and `claimRoot`, every path the judge path writes to now resolves under the password database's home rather than any variable — which is why the audit log, the judge log and the claims directory all live under `~/.local/state/coop` whatever `$XDG_STATE_HOME` says. The hub's own `hooks-settings.json` still honours it: that one is written at launch from the operator's shell, where the variable is theirs and not a monitored session's.

The verdict is `{action, digit, reason}`, and nothing in it is a command. `parseVerdict` re-validates every field — a known action, a single-digit digit, a digit whenever the action is `answer`, a non-empty reason — because a malformed verdict must be a no-op, not wrong text on a row. `applyVerdict` does not route it, because there is only one destination: **every verdict is a `Note`**, keeping the digit as the suggestion `space` applies. The prompt still offers both actions and `parseVerdict` still validates both, deliberately — an `answer` differs from an `escalate` only in how sure the model was, and the model is asked what it *would* do while coop decides what that is worth, which is one less thing the prompt can get wrong than telling it what it is allowed to do.

**There is no `Answer`, and no send path out of the judge at all** — which is also why there is no gate on one. A reader looking for the five an autonomous answer would need (a mode saying answering is allowed, a refusal to target coop's own sessions, `pane_current_command` in an allowlist, `NeedsInputScreen` proving a numbered dialog is actually on screen, and a last-moment `@coop_status_since` re-check that the episode on screen is still the one the verdict was formed about) will not find them, because gating a send is a strictly worse answer than not having one: every one of those checks reads state that can go stale between the read and the keystroke, and the `since` check in particular has one-second resolution, so a waiting→busy→waiting round trip inside a second was indistinguishable. The place that reasoning still lives is the *human's* keystroke: `space apply N` goes through the TUI's own `answerCmd`, the same path the `0-9` keys take, which re-reads `pane_current_command` at send time and refuses anything outside the hub's `-allowed-cmds` (`hub.DefaultAllowedCmds`, `claude,node`), because the poll snapshot can be a second stale and a dead claude leaves a shell that must never receive keystrokes. The stale-episode problem those gates existed for is now a human's to see: the note and its digit sit on the row under the screen the human is looking at, and `ApplyHook` retires both the moment the status leaves `waiting`. `Note` is an internal call target, not a CLI surface — there is no verb left for a model to reach for, only `coop peek` as a human debug aid.

`arbiter.model` defaults to `sonnet`, and not to the cheapest model that can emit the schema. The note a human reads on the row — and the digit they apply with one key — *is* the product here, not a footnote to a keystroke, and producing it means summarizing a captured terminal an attacker can influence into one line someone will act on, which is a harder job than picking a branch of a fixed output shape. One episode is still a single turn over a bounded prompt, so the better model is worth what it costs; an operator who disagrees sets `arbiter.model`. That key is read from `config.DefaultPath()` and nowhere else — **not** from a flag, **not** from the environment, and **not** from a tmux option — and the same holds for the config *directory*, which is where `arbiter.md` (the policy the judge obeys) lives and is a parent `claude` discovers a `CLAUDE.md` from, so a session that could name it would be writing its own rules. Both alternatives were tried and both are writable by the very sessions being judged: `coop hook` runs inside the monitored pane, so its environment is that session's to set — an `env` block in a repo's `.claude/settings.json` is enough, no code execution needed — and `$TMUX` in that same pane points at coop's own socket, making `tmux set -g` one approved tool call away, strictly easier than exporting a variable, which needs a restart to take. `judgeConfig` therefore needs only two cases where it once needed three: a file that parses is obeyed, and anything else falls back to the default model, with a present-but-unparseable file **logged** rather than swallowed, because the operator wrote something they believed was in effect. Failing to that default is no longer a safety question — a broken config costs a judgement from a different model, not a wrong keystroke.

**None of this is a security boundary against a hostile session.** coop and the sessions it watches run as the same user on the same tmux server: a session with code execution can set `@coop_arbiter_mode`, park notes on any row, rewrite `config.json` and `arbiter.md`, or replace the coop binary. What the design buys is a smaller blast radius for an *unattended judge misfiring* — a wrong verdict, a stale screen, a prompt injection that lands — since the worst it can now produce is wrong text and a wrong digit sitting on a row that a human still has to read and press a key for, plus a durable audit record of every escalation. That is not a sandbox, and no comment or doc here should imply otherwise.

A verdict's digit is a separate option from its text (`@coop_arbiter_suggest` vs `@coop_arbiter_note`), so `space` applies a field rather than a number parsed out of prose, and a `space apply N` chip joins the hints only while the selected row has one. A verdict with no digit clears any an earlier one left, since a stale suggestion under fresh text is the one way that key sends a wrong answer, and `ArbiterSuggestOf` re-checks the single-digit shape on read because the TUI hands the value straight to send-keys. The row's arbiter line is the note and nothing else — the arbiter never answers, so there is no past answer to report on it. Episode cleanup — retiring `@coop_arbiter_note` and `@coop_arbiter_suggest` — happens in `ApplyHook` when a status transition leaves `waiting`; panes that publish no hook state never get that transition, so `RetireStaleEpisodes` covers them from the hub poll instead. Diagnostics go to `~/.local/state/coop/judge.log`: failures, raw verdicts, and **one line per episode** — pane, session, `dialog=` (`NeedsInputScreen`'s own verdict on the captured screen), `agent=`, and the verdict's action and reason. That line exists because a log of failures only cannot tell "escalated: cannot see the permission dialog" apart from a capture that genuinely showed none. It is a summary and never the screen itself — capture output is untrusted and a terminal's worth per episode would bury the log it is meant to make readable. For the same reason a failed `claude` run's stderr is folded into the returned error (`judgeRunError`, bounded and flattened by `sanitizeNote`): `cmd.Output` parks it in `(*exec.ExitError).Stderr` where nothing read it, and the judge is detached with both its own streams on `/dev/null`, so `judge.log` is the only channel it has — a bad model id used to log `exit status 1` and nothing else. `arbiter-audit.jsonl` beside it stays what it was in shape, a record coop never reads back, but there is only one action left in it: every line is an `escalated`, carrying the suggestion digit when the verdict offered one. Older lines saying `answered` still parse — the fields are additive on disk and nothing reads them.

Four gaps are accepted rather than closed. Turning the arbiter on while sessions are already sitting at prompts judges none of them: no further hook event fires for a pane that is already waiting, so those episodes stay unjudged until the next one — deleting the launch catch-up was the price of having no hub-side path at all. A pane with no hook state (started outside coop, or under `-hooks=false`) is never judged, though its stale markers still retire via the poll. There is no global cap on concurrent judges — one per episode is the only limit, and episodes are as concurrent as the sessions are. And `judge.log` is never rotated.

### The toolbox (`internal/toolbox`, `cmd/coop/toolscli.go`)

Every session coop launches gets its repo's command-line tooling out of a container rather than off the host, through shims on `PATH` that nobody — operator or model — has to know about. One container per repo, `coop-tools-<slug>` (basename plus a hash of the cleaned absolute path, so a human reading `docker ps` can tell which repo it belongs to and two checkouts of one project do not share it); every session on that repo execs into the same one, because the unit a toolchain is declared for is the repo, not the session. **There is no new state store.** Docker is the database the way tmux is — `docker ps --filter label=coop.managed=true` *is* the query — and coop persists nothing about containers: no file, no tmux option, no refcount. `Engine`/`ExecEngine`/`fakeEngine` deliberately mirror `Tmux`/`ExecTmux`/`fakeTmux`, and unit tests never start a container; real docker is `scripts/toolbox-smoke.sh`, which skips with a message when docker is absent the way `e2e-smoke.sh` requires tmux ≥ 3.2.

The repo bind-mounts **at its own host path** — `-v <repo>:<repo>:rw`, `-w` the pane's cwd — never at `/workspace`. Path identity is the invariant the rest rests on: a traceback, a `--help` example, an absolute path in a config file and whatever claude then hands to `Read` all name the same file, so there is no translation layer to get wrong and no failure mode where claude reads `/workspace/foo.py` out of command output and cannot open it. `ResolveCwd` falls back to the repo root for a cwd the container cannot see, since a command run from an unmounted directory should work on the repo rather than fail. The mount is read-write on purpose: formatters and code generators are a large share of why a tool is worth shimming at all, and `--user $(id -u):$(id -g)` means what they write is already the invoking user's. Two further standard mounts — `/tmp`, because the session scratchpad lives there and it is already shared same-user space, and a persistent per-repo `HOME` under `~/.local/state/coop/toolbox/<slug>/home`, because that uid has no passwd entry inside and pip, npm and gh all need a writable home. `GOCACHE`, `PIP_CACHE_DIR`, `npm_config_cache` and `CARGO_HOME` resolve into that home, which is load-bearing rather than hygiene once a repo is all-in: without it every idle-out is a cold rebuild, and the default location for environment-coupled state becomes the working tree. **The sharp edge is that `$HOME` is not the user's home** — `go install`, `pip install --user`, `npm i -g`, `cargo install` all succeed, work for the rest of that command, survive an idle-out, and are invisible from the host forever. Only an install targeting a declared mount reaches it.

Two things happen at different times, and separating them is what keeps this simple. **At session create**, `Prepare` resolves the image, reads its manifest and writes the shims — and starts nothing. That ordering is forced rather than chosen: shims cannot be generated from a running container, because nothing starts the container until a shim is called, which is also why `ReadManifest` is a one-shot `run --rm --entrypoint cat <image> /etc/coop/tools`. **The container starts on the first shim call**, and that same path is the self-heal: `ensureContainer` creates one whenever `Inspect` does not show one running **on the image the repo resolves to now**, so a first use, a return after an idle-out, a recovery from `docker rm -f` and a session that predates the toolbox are all one code path with one thing to get right. The image half of that check is not decoration: a container from before an overlay edit is still up and still holds the repo's one container name, but does not carry the tool the newly written shim names, so a second session would exec into it and get `executable file not found` for a tool the repo had just declared. It costs nothing to check, because `ImageTag` hashes files rather than asking the engine — the reconcile rides on the one `inspect` the exec path already makes, and the old container is `rm -f`'d first only because it holds the name.

**Stop is the container's own job.** PID 1 is `ReaperScript`, not `sleep infinity`: it wakes every 60s and exits once nothing has run for `idle_timeout`, and `--rm` means exiting removes it. Two liveness signals, because either alone has a hole — "a process besides PID 1" catches a long command directly, so a forty-minute test run keeps its own container alive by definition, but it samples once a minute and can miss a series of short ones; the activity file `coop tools exec` touches before every command catches those. It is `bash` so `$EPOCHSECONDS` and the glob count are builtins, since a reaper that forked to measure its own idleness would never be idle. Reaping from the hub poll was considered and rejected on three counts: it **requires a hub**, and poll-based reaping would stop the moment the TUI quits, which is precisely when the containers should go away (the arbiter already establishes that coop's background work must not depend on a hub being up); it **cannot see work in flight**, since panes are a proxy for liveness and a background process in a closed session would get its legs cut; and it **is state**, labels or refcounts to keep in sync with two hubs on one socket racing over them. An aggressive timeout is safe *because* the shim self-heals — an idled-out container coming back is a ~1s hiccup on one command, with the image already built and cached.

The governing rule for a repo is **all-in or all-out, never split**: builds and tests belong in the toolbox whenever the repo's toolchain is there at all. The failure mode to avoid is not "a build ran in a container", it is one toolchain straddling two environments — `go test` inside and `go build` outside means claude has to know which is which, and the shim exists precisely to make that invisible; the result is a binary written into a home nobody looks in and reported as a success. So the base image ships **no compilers**: a repo commits its whole toolchain to the container deliberately, in its overlay, or not at all. coop's own repo is all-in (`.coop/tools.Dockerfile`), which is the opposite of the first-glance read — coop has to absorb tmux 3.4 vs 3.5 differences and a host can only ever have one tmux, so pinning it makes the version the suite runs against a declared property of the repo. That pin is *installed and not shimmed*, for the reason the reserved set below exists. The base image's manifest is narrow for a related reason: `git`, `gh` and `make` ship in it and none is shimmed by default, since a container `gh` has neither `~/.config/gh` nor `GH_TOKEN` (the environment allowlist passes neither) and would answer a working `gh pr list` with "please run: gh auth login", while `make` drives a whole build in an image with no compilers — the split toolchain this rule exists to prevent, handed to every zero-config repo with no opt-in. A repo that wants either shims it in its overlay, where it can also supply what that tool needs. Three carve-outs remain and all three are structural: `scripts/toolbox-smoke.sh` runs on the host because it tests this feature and needs a docker socket, which is never mounted; running coop is a host activity, since it attaches to the host tmux server and watches host processes; and an editor's language server is a host consumer that wants a host Go. The achievable claim is that *claude's* toolchain is containerized, not that the host has nothing on it. Nothing detects a split repo, either — an overlay carrying `go` while the host also has one is indistinguishable from the intended arrangement, so the rule is a convention and the symptom is an artifact turning up somewhere unexpected.

**A repo's commands are declared in one of two places, and a repo that declares them explicitly wins outright.** A `commands` block in `.coop/toolbox.json` is the **complete** list for that repo — it replaces the image's manifest rather than extending it, so a repo declaring `commands` and omitting `python3` does not get `python3` from the base image. That is the cost of explicit and it is the point: one file you can read to know everything shimmed, with no merge semantics to reason about, no `extends`, and no way to subtract from an inherited set. Absent the block, the image's manifest is the whole story, which keeps the zero-config path (no `.coop/` at all → the base image's tools) working exactly as before the field existed, and makes the field purely additive to every repo that predates it. `CommandNames` reports *declared* separately from *empty*, because `{"commands":{}}` is a repo saying "shim nothing" and must not fall through to the image. Being declared is also the only route to a grant (see the init skill above): `allow` — default-deny — is what turns a declared command into the `Bash(...)` rule coop injects, and since the injected rules are filtered again through the shims that exist (`toolbox.Grants`), "allowlisted but unshimmed" is unrepresentable rather than merely discouraged. `AllowSpec` takes `true` for the whole command or a **list of argument prefixes** (`"allow": ["build", "test"]` → `Bash(go build *)`, verified to match a two-token prefix the same way a one-token one does). The list form is deliberately *not* sold as a restriction, and the docs say so in as many words: on a compiler it restricts nothing, since `go test` runs whatever is in the tree and a test that shells out to `go install` gets there anyway. What it buys is **where the prompt lands** — `go install` writes into a container `$HOME` invisible from the host, so putting the friction on the surprising verbs rather than the inner loop is worth a feature even though it contains nothing. On a service CLI (`terraform plan` vs `apply`) the same shape does draw a real line, because neither subcommand can reach the other; that is the one case where narrowing means what it looks like. Entries go through `safeArg`, which allows plain words, paths and dashes and drops anything — a `)` closing the rule early, a `*` widening it, a quote or shell metacharacter — that would make the written rule mean more than the file says; a dropped entry costs one grant, never the file. Both sources run through the same `safeTool`/`reservedTools` filtering, since a name that could escape `ShimDir` or shadow coop's own plumbing is no safer for being written in JSON.

`MissingTools` is the check that **replaces co-location**, and it is the one thing the move genuinely cost. While the manifest lived in the Dockerfile it sat directly under the `RUN` that installed the binary, so declaring without installing took effort; two files can now disagree silently, and the symptom is bad — the shim exists, so the command is granted if it was marked `allow`, and it dies at exec on docker's bare `executable file not found` naming a tool the repo believed it had declared. So `Prepare` probes the image once for the whole list (`sh -c 'for t in …; do command -v "$t" …'`, one run rather than one per tool; the names are already `safeTool`-filtered so none can carry a metacharacter into that script) and returns the unresolvable ones. They are a **warning, not an error, and the shims are written anyway**: silently skipping one would hand that command to the host, which is precisely the failure a declaration exists to prevent, and failing loud at exec is the toolbox's existing stance for anything about the container. A probe that cannot run reports nothing rather than failing — a diagnostic must not stop a session being created. The warning goes to `build.log` on the asynchronous path and to **stdout** from `coop tools rebuild`, which is the one place a human is watching, and it is phrased as the two edits that fix it, since a bare tool name reads like a coop bug rather than a disagreement between two files the repo owns. On the declared path this costs nothing: `ReadManifest`'s container run is skipped, so the probe takes its place.

**The image declares its own tools**, in a manifest at `/etc/coop/tools`, one command per line; coop shims exactly those when the repo declares nothing. A repo adding a tool appends one line, so there is no list in coop's config to drift out of sync with the image and no per-repo config at all in the common case. What belongs there is language runtimes, package managers and service CLIs — each shim costs ~30–80ms of `docker exec` startup, which is noise for `python3` or `mongosh` and ruinous for `grep`/`ls`/`cat` in a loop, and claude reaches for its own `Grep`/`Glob` tools for that work anyway, which run on the host regardless. Because the image declares the list, that is a rule about how an image is authored rather than code. `ParseManifest` does enforce two things. A line that is not a plain command token is dropped, since the manifest comes from an image a repo authored and a name carrying a slash or a shell metacharacter would either write a shim outside `ShimDir` or inject into the shim body. And a small **reserved set** — `tmux`, `docker`, `podman`, `coop` — is dropped whatever the manifest says, because those are the binaries coop itself runs by bare name *from inside a monitored pane*, where the shim directory is first on `PATH`. A shim for one of them does not fail loudly, it silently reroutes coop's own plumbing: `internal/hub` shells out to `tmux`, so every `coop hook` write would go through the container's tmux talking to the host's server across a protocol it does not speak — and since `coop hook` is silent and always exits 0, the entire hook status tier and the arbiter would degrade to title-only with nothing logged anywhere. The engine names are the same shape one hop further on: `coop tools exec` inherits that `PATH` and resolves the engine through it, so a shimmed `docker` means shim → `coop tools exec` → shim, until the process limit. Installing such a tool in an image stays fine and is sometimes the point (coop's own overlay pins `tmux` and never shims it); it is the `PATH` entry that breaks. The set is fixed rather than derived, which leaves one residual gap: a `toolbox.engine` set to something exotic is not in it, and a repo that shimmed *that* name would recurse. Dropping the line rather than the manifest is right throughout — a bad entry costs one missing shim and the host's copy of that tool, where refusing the whole file would cost every shim.

The base Dockerfile is `go:embed`ed in the binary and built on first use — no registry, no second repo to keep in sync — tagged `coop-tools:base-<hash of the Dockerfile>` plus a moving `coop-tools:base` that overlays name in their `FROM` line, so an overlay never writes a hash and a coop upgrade rebuilds by itself. It is debian-slim rather than alpine because musl breaks enough pip wheels that alpine would manufacture exactly the "why won't this install" problem the feature exists to remove, and it deletes Debian's PEP 668 `EXTERNALLY-MANAGED` marker: the container *is* the environment, there is no host python for the marker to protect, and leaving it would fail every `pip install` in an overlay or a session. A repo's optional `.coop/tools.Dockerfile` is built as `coop-tools-<slug>:<hash of overlay + base>`, so editing either rebuilds, with the `.coop` directory as the build context — an overlay that `COPY`d from the repo would make the image depend on working-tree state. `.coop/toolbox.json` carries the two things a Dockerfile cannot state: `network`, the docker network to join (explicit, never inferred from a nearby `docker-compose.yml`, because guessing a network name is the kind of magic that is charming until it attaches to the wrong one), and `mounts`, extra host paths. A mount names a host path and appears at that same path — **no `src:dst` remapping**, since that would reintroduce the `/workspace` translation problem somewhere new — and is **read-only unless `:rw` is explicit**, because `~/.local/bin` needs write and `~/.aws` emphatically does not. `~` expands against the password database, as everywhere else in this repo. coop **refuses to mount `~/.config/coop` or `~/.local/state/coop`**, any parent of them (so `~` is refused too) and anything under them; not as a boundary, but for the same reason `JudgeEnv` builds the judge's `HOME` out of the password database — it costs one check and it stops an unattended own-goal where a container rewrites `arbiter.md` or the claims directory by accident. The descendant is the sharper of the two directions and was the one initially missed: `~/.local/state/coop/toolbox/<slug>/bin` is *another repo's* shim directory, `#!/bin/sh` scripts that execute on the host the moment that repo's session runs `python3`, and naming it directly was allowed while naming its parent was not.

**The container inherits almost no environment**: only `TERM`, `LANG`, `LC_ALL`, `LC_CTYPE` and `TZ`, which decide how text renders and nothing else. The image's own `ENV` is authoritative, so repo-specific environment belongs in the overlay, declared once and travelling with the repo rather than depending on what the operator's shell happened to export. Failure is **fail open at generation, fail loud at exec — but only about the container**. `newToolboxCmd` returns `nil` when the toolbox is disabled or no engine is installed and coop behaves exactly as it did before the feature existed, and it parses `toolbox.idle_timeout` there too, where a bad value still costs nothing but a message and an untouched `PATH`; a failed `Prepare` runs in a goroutine and lands in `~/.local/state/coop/toolbox/build.log` (the TUI has no room for a build error and the goroutine has no terminal — the same reasoning as `judge.log`), while a container that will not start prints one line naming `coop tools rebuild` rather than a mystery. The asymmetry at exec time is deliberate and was got wrong first: **coop's own settings fail open, the repo's container fails loud**. Shims are files on disk and the `PATH` prefix is already inside a live session's command, so `config.json` going unparseable — or an `"enabled": false` the docs describe as the off switch — would otherwise hard-fail *every* shimmed command in *every* running session at once. So when `toolsSettings` will not resolve, `execHost` looks the tool up on a `PATH` with coop's shim directories stripped (`LookHost`, never `exec.LookPath`, whose `$PATH` is the shimmed one) and execs the host's copy silently, which is what that command ran before the toolbox existed; only with no host copy at all is the cause printed. A repo's own `.coop/toolbox.json` stays loud, because it is one repo's file about one repo's container. That loudness has a **migration edge worth knowing before widening the schema**: the shims call whatever `coop` is installed, so a repo that adopts a new field or a new form of an existing one — `"allow"` growing from a bool to a bool-or-list is the first instance — hard-fails every shimmed command in that repo under any older binary, including the `go` needed to build the newer one. Observed, not theorised, while landing that very field. Nothing here should change: the alternative is a repo config that silently means something different per binary version, which is strictly worse than a parse error naming the file. The ordering it imposes — install, then edit — is a doc line (`docs/toolbox.md`'s gotchas) rather than code. The `PATH` prefix is injected whenever the toolbox is on and the engine is present, *before* the shim directory necessarily has anything in it: the path is deterministic from the slug, and a `PATH` entry naming a briefly empty directory is harmless — a command in that window finds the host's tool, as it would today. The shim directory goes **first**, so the container's `python3` beats the host's, which is the point; an absolute path still bypasses it, which is escape hatch enough. The per-repo `HOME` is **discoverable rather than disguised**, and the distinction matters because that directory is bind-mounted at its own host path (`-v home:home:rw` with `HOME=` that path), so a path a tool prints inside is openable outside verbatim — the same path identity the repo mount buys. What surprises people is not a wrong path but the wrong *home*, so remapping `$HOME` to look like the user's own would trade an honest surprise for a dishonest one: `/home/<user>/.local/bin/x` would read as correct, resolve to something else, and give no way to tell — the `/workspace` translation problem made invisible, and structurally worse since most repos live under `$HOME` and would end up as a fake tree with real-host islands punched through it. So the fix is signposting: `coop tools home [repo]` prints the path and nothing else (stdout stays pure so `ls "$(coop tools home)"` composes; the "not created yet" note goes to stderr) and answers for any repo whether or not a container is running, unlike `coop tools ls` — "where did my `go install` go" is usually asked *after* an idle-out. Alongside it `WriteHomeMarker` drops a `README.coop-toolbox` in the directory naming the owning repo and the declared-mount escape hatch. It is deliberately **not** a dotfile: the whole point is to be seen by the `ls` of someone who arrived by following a path, and a dotfile is invisible at exactly that moment. It is rewritten on every container start rather than seeded once — a small write per start, not per command — so it self-heals a deleted marker, and best-effort, since documentation must not stop a container coming up.

The other half of that signposting is told to the session rather than left to be found: `SessionNote` (`internal/toolbox/note.go`) renders the shim list, the host-path identity and the container `$HOME` into a paragraph `coop hook` returns as `SessionStart` `additionalContext`. A shim is deliberately invisible — claude types `go build` and the permission layer sees exactly that — which is right on the common path and wrong at the moment something fails, where docker's bare `executable file not found` reads as a coop bug and a `go install` vanishes with no hint that it went anywhere. **It is not a `CLAUDE.md`, and the difference is the whole point**: the only files claude discovers are the repo's, which is committed and so reaches sessions coop did not launch — where no shim is on `PATH` and the note is simply false, the identical leak that put the toolbox grants in the injected `--settings` rather than in `.claude/settings.json` — and the user's global one, which reaches every project on the machine. This vehicle reaches exactly the sessions coop launched, writes nothing to disk, and is rebuilt from the running binary at every event. It is emitted on **every** `SessionStart` source, `compact` emphatically included, and that is what makes it beat both a `CLAUDE.md` and an `--append-system-prompt`: those are read once at launch, and the failure being guarded is a model that stopped knowing its toolchain is containerized 200k tokens in, so returning after each compaction is the mechanism rather than a bonus. The list comes from the shims **on disk**, exactly as `Grants` does and for the same reason — `Prepare` builds asynchronously, so a first session on a fresh clone starts before any shim exists and a build can fail outright; no shims means no note, because a session told its commands are containerized at the moment they are not is worse off than one told nothing. Which session it is, is read off `$PATH` (`ShimDirOn`) and not off the payload: a hook's cwd is wherever the session happens to be and may be well below the repo, the slug is hashed so there is nothing to reverse, and a shim directory being on `PATH` *is* the fact in question. Content is facts and one prohibition — don't route around a shim with an absolute path — never rules; all-in/all-out, the reserved names and the build context stay in `docs/toolbox.md` and `/coop:init`, since a third copy here would be the one that goes stale. The cost is one invariant: `coop hook` printed nothing at all before this, and now stdout is meaningful on one event, so the emission is gated on `SessionStart` alone and every failure path in it stays silent (`TestRunHookCLINoOps` asserts the empty stdout that used to be structural). That Claude Code consumes the envelope was verified against a real `claude -p`, not assumed.

`coop tools grants [repo]` answers "why is this still prompting" without starting a session to look at the injected settings file — the rules on stdout so it composes, and on stderr the two things that explain an empty list: a rule withheld because its shim is not written yet (the case worth naming, since it is "the build has not finished" rather than "you never declared it"), and the reminder that a running session read `--settings` at launch. It shares `hub.BashRule` with the writer rather than formatting the rule a second time, because a debug aid that renders what it reports differently is worse than not having one. **Every subcommand's repo argument goes through `toolsRepo`, `exec` included.** That path becomes a slug, a container name, a `-w` and a `-v <repo>:<repo>:rw` all at once, and `Slug` *cleans but does not absolutize* — so a relative one slugs to `repo-<hash of ".">`, a name belonging to no repo, builds a second image under it, and only then hands docker a `-v .:.:rw` it rejects. `exec` read its argument verbatim until that was noticed, which never bit in production because the shims embed an absolute path, and bit immediately the first time a human typed `coop tools exec . id` to debug something. Routing it through `toolsRepo` is safe precisely because `filepath.Abs` is `Clean` on an already-absolute path: the slug of a container already running cannot shift under it, and only the broken case changes. `TestToolsRepoAbsolutizes` covers the resolution; the wiring itself is not unit-tested, since `toolsExec` goes straight to a real engine — `scripts/toolbox-smoke.sh` is what exercises it. `coop tools ls|up|stop|prune|rebuild|shell|home|grants` is the human surface and none of it is on the normal path; `coop tools exec` is what the shims call, and its **last** attempt is always a `syscall.Exec` of the engine binary, so exit codes and signals pass through exactly with no wrapper left in the middle of a `^C` (`-i` for stdin, never `-t` — the Bash tool has no tty). It is the last rather than the only attempt because the spec asks for one retry, and a process that has replaced itself cannot retry anything: a container that was *already* up when `Inspect` looked can be gone by the time the engine looks (a human's `docker rm -f`, or the reaper's own exit), so that one case runs as a child (`runEngine`, every fd inherited), and a non-zero exit with the container no longer running is restarted and re-run — once, through the exec. A container coop just started needs none of that and goes straight to the exec. The child catches and drops `SIGINT`/`SIGQUIT` rather than dying on them, so a shell does not get its prompt back while the command is still dying; *caught* rather than ignored is load-bearing, since Go resets caught signals to the default across an exec while an inherited `SIG_IGN` would survive into the container's command and make `^C` do nothing at all.

**None of this is a security boundary.** The repo is bind-mounted read-write at its host path, the container runs as the invoking user's uid, `/tmp` is shared, and a container joined to a compose network reaches whatever that network reaches — anything with code execution inside can rewrite the repo and the user's scratch space. **The docker socket is never mounted**, in any code path: that single line would turn every shimmed tool into host root and is the one mistake in this design space that is not recoverable. It is also why `toolbox-smoke.sh` stays on the host. What the toolbox buys is a reproducible toolchain and a clean host, and no comment or doc here should let the word "container" imply a sandbox.

Gaps accepted rather than closed. A repo with its own compose stack ends up with two container stories — `docker compose exec app` for its services, the toolbox for its scripts; the clean resolution is a later `.coop/toolbox.json` naming an *existing* compose service to exec into, deliberately not in v1 because the build path is what serves repos with no container story at all. Sessions started outside coop get no shims, since `PATH` is injected at launch — the same shape as the hook status tier, where a pane that publishes nothing falls back to what the host provides. Isolation is out of scope: `Read`, `Edit`, `Glob` and `Grep` run in-process on the host, so the repo stays host-visible no matter what this design does, and full isolation is only reachable by moving `claude` itself into a container. And there is no image garbage collection beyond `coop tools prune` — superseded base and overlay images accumulate across upgrades until pruned by hand.

### The init skill (`internal/skills`)

Every session coop launches carries a Claude Code plugin holding one skill, `/coop:init`, which authors a repo's `.coop/tools.Dockerfile`. The shape is `hooksettings.go` one hop over and deliberately so: `WritePlugin` materializes a `go:embed`ed tree under `$XDG_STATE_HOME/coop/plugin` and `WithPlugin` appends `--plugin-dir` the way `WithHookSettings` appends `--settings`. `--plugin-dir` loads a plain directory for one session — no marketplace entry, no `known_marketplaces.json`, no install step — which is what makes regenerating the tree on every hub launch cheap enough to be the only mode; like `hooks-settings.json` it is coop infrastructure that always matches the running binary, never a file the user is meant to edit. Nothing lands in `~/.claude`, so a session started outside coop is unaffected, exactly as it is by the hook tier.

`-plugin`/`COOP_PLUGIN=0` is **separate from `-hooks`** even though both happen to require a real `claude` that accepts flags (`e2e-smoke.sh` sets both off, its fake claude being `sleep 300`). One switch named after the other would mean the e2e turns the status tier and the arbiter off in order to say something about a skill, and the two inject different things for different reasons. Both propagate through `createArgv` to the hub the bootstrap starts, or a `coop -plugin=false` outside tmux would launch a hub that ignored it.

`WritePlugin` builds in a sibling temp directory and renames. A missing `--plugin-dir` is tolerated by `claude` — verified, it starts normally — so the remove/rename window costs at most one session its `/coop:init`, exactly as `-plugin=false` would; a *partial* tree is the case worth avoiding, since a manifest with no skill under it is worse than no plugin. Removing rather than merging is what stops a skill renamed across coop versions leaving a stale second copy loaded.

The skill's reference file is **`docs/toolbox.md` itself**, embedded through a `docs` package and written into the skill's directory at materialization. The rules that bite silently — the four reserved names, all-in/all-out, installed ≠ shimmed, the build context, the `$HOME` gotcha — already live in that guide and in this file; a third copy inside `SKILL.md` would be the one that goes stale, so `SKILL.md` holds only the procedure and defers. That is also why `WithPlugin` appends `--add-dir` beside `--plugin-dir`, and why it is not optional: a session's filesystem scope is its working directory, and the skill resolves the reference's correct absolute path and is then refused. The refusal is **scope, not permissions** — an allow rule in the injected settings does not substitute, which was checked rather than assumed. The scope granted is the plugin directory alone and never its parent, so the claims directory and the audit log stay outside it; `--add-dir` also grants write, which is worth naming and not worth avoiding, since this is the same user on the same machine (a monitored pane's `$TMUX` already points at coop's socket) and the plugin is regenerated from the binary at every launch, so anything written into it is erased rather than trusted. `--add-dir` is variadic, so it has to stay the last thing on the command.

**The skill writes nothing in `.claude/`, and the reason is the whole permission design.** A shim does not change the command string — claude types `mongosh --eval …` and the permission layer sees exactly that — so the way to stop prompting for a containerized tool is to allowlist the bare name, which is sound only while a shim is on `PATH`. A `.claude/settings.json` is committed, so the same rule reaches sessions coop did not launch, where there is no shim and it now means "run the host's copy, unattended, no prompt": a grant made under an assumption that silently stopped holding. The first design answered that with a `PreToolUse` guard hook re-checking the assumption at call time, which worked and was the wrong shape — it compensated at runtime for a grant that should never have been committed, cost two gated writes the human had to approve, and left a copied shell script in every repo that could not be updated when coop's own copy changed. **The grant now lives in the settings file coop injects** (`hub.WriteSessionSettings`, `--settings`), which reaches exactly the sessions coop launched — exactly the sessions that have the shims the grant assumes. Nothing is committed, so nothing leaks, so there is nothing to re-check and no guard to install, update or get wrong. `toolbox.Grants` derives the rules from the shims **actually on disk** rather than from the declaration, which closes the one gap the guard was covering that its removal would otherwise reopen: `Prepare` builds asynchronously, so a first session on a fresh clone launches minutes before any shim exists, and a build can fail outright — deriving from the declaration would hand those sessions a `Bash(go *)` with the host's `go` behind it. Deriving from the directory means a grant cannot outrun the tool it grants, with nothing to evaluate at call time. The cost, and it is a real one: grants apply from the *next* session, since `--settings` is read at launch. That is stated in `SKILL.md`'s closing step and in `docs/toolbox.md`, because a user who is not told reads it as the setup having failed. That the injected file works at all is **verified, not assumed** — a `Bash(...)` rule delivered by `--settings` turns a blocked call into an executed one, the `Bash(<tool> *)` wildcard form matches, and hooks and permissions coexist in one file with the hooks still firing. The skill is still told in as many words never to write `.claude/settings.json` or `.claude/hooks/*`, through Write or through Bash, and `TestSkillWritesNothingInClaudeDir` keeps both the instruction and the absence of the guard asset named: the gate on those files is Claude Code's own and is correct, and a skill with no reason to touch them must not learn to.

The skill itself asks **all-in or tools-only and waits** rather than inferring it: that call moves a repo's compiler off the host, and the split toolchain it guards against is the failure mode the toolbox exists to prevent. It also stops before `coop tools rebuild`, which is the human's to run — it takes minutes and its whole value is build output on a terminal the skill does not have.

### Launch flow (`cmd/coop/main.go`)

Run outside tmux, coop bootstraps the server itself: one tmux invocation chains `start-server`, the built-in defaults (`tmuxDefaults`), config.json `tmux` overrides, and `new-session` running coop, then execs into `attach-session`. `-f /dev/null` keeps the user's tmux.conf off the socket. **Every chained tmux command must be idempotent** — the chain re-runs each time a hub launches against a running server (so plain `set`, never `set -a`). Run inside tmux, it goes straight to the TUI. Hub sessions are named `roost`, `roost-2`, … so several hubs (one per monitor) share a socket; a detached hub is reattached rather than duplicated.

### TUI conventions (`internal/tui/model.go`)

- All tmux I/O happens inside `tea.Cmd` closures that capture what they need **by value** — the Model is never touched from inside a Cmd.
- `Update` returns at most one command per message ("single-command invariant") so tests can drive it message-by-message; chains are expressed as message → command → message (e.g. `livePaneMsg` → `resizeSelf` → `resizedMsg` → `retarget`).
- Nearly all tmux writes are best-effort with a comment saying so — a failure leaves state stale and the next poll tick retries/self-heals. Follow that pattern.
- The footer is a message box above the key hints: `viewFooter` renders the first non-empty of `actionErr`, `errMsg`, `arbiterDetail()`, word-wrapped by `wrapMsg` and capped at `min(msgBoxLines, height/4)` visible lines, with `pgup`/`pgdn` scrolling and a `pgup/pgdn scroll` chip that appears only while it overflows. Rows are scarce at the pinned `navWidth`, so the box takes none when there is no message. `Update` is a thin wrapper over `update` that calls `syncMsg` — the one place the scroll rewinds when the text changes — so the single-command invariant still holds. Confirm prompts (`kill X?`, `quit coop?`) bypass the box and own the whole footer; they are questions, not messages.
- The `n` picker ends in a `+ add new repo` row: `repoIdx` one past the end of `filteredRepos()` selects it, `enter` opens a path prompt (`adding`/`repoPath`), and a good path goes through the injected `addRepo` writer → `repoAddedMsg` → `createCmd`, so the session starts in the repo it just saved. An empty repo list still opens the picker — that row is the only way to configure the first one. `pickerLayout` is the single source of the body's geometry: `viewPicker` draws from it and `pickerRowAt` maps clicks back through it, the way `paneAt` mirrors `viewNav`. It pins the add row to the bottom of the frame and scrolls the list under it, so a long config can't push the row out of reach.
- The live preview is a real nested tmux client (`TMUX= tmux attach -f ignore-size`) in a split pane, retargeted by `respawn-pane` when the selection changes; `ignore-size` keeps it out of window-size negotiation (`HasPrimaryClient` distinguishes it from real clients).

### tmux targeting gotchas (see comments in `internal/hub/tmux.go`)

Exact-match `=` prefixes and trailing `:` on session targets are load-bearing (`"=name"` vs `"=name:"` vs bare `name:` differ per command); don't simplify them without reading the adjacent comment.

Versions below 3.5 differ in two ways coop has to absorb, since Ubuntu 24.04 LTS ships 3.4. **`-F` output is run through `vis(3)`**, so the `\x1f` field separator arrives as the four characters `\037` — every parser splits with `splitFields`, never `strings.Split` on the raw byte. Getting this wrong is not a cosmetic failure: `parseMarkedPane` misses the live pane, so the TUI splits a fresh one every poll tick. And **`allow-set-title` does not exist**, so `livePaneOptions` sets it best-effort. More generally, a live pane that exists is adopted even when the command that made it returned an error — dropping the id is what turns any such failure into one new pane per second.

## Testing

Unit tests never touch a real tmux: `hub` tests parse canned output or use `fakeTmux`; `tui` tests construct a `Model` and feed `Update` messages directly, asserting on returned commands' messages. `scripts/e2e-smoke.sh` covers the real-tmux integration (discovery, status, live preview, retarget, create, kill, quit) — run it when changing launch, live-pane, or tmux plumbing.

**Never put paths from the developer's own machine into tests or fixtures** — no `/home/<username>/…`, no real home directory, no absolute path to this checkout. Fixture paths are always generic (`/home/user/coop`, `/home/user/Documents/coop/git/coop`, `/home/user/sprocket-v2`); anything the test actually writes to goes under `t.TempDir()`. The same goes for repo and session names — invent them (`sprocket-v2`, `alpha`, `beta`), never borrow a real project's. Tests must pass for any user on any machine, and a real path leaks the developer's environment into the repo.
