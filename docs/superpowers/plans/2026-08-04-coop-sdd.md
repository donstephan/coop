# coop-sdd Implementation Plan

> **For agentic workers:** execute with the operator's personal `sdd`
> skill (their standing policy — NOT superpowers:subagent-driven-development).
> Edits land in the working tree, no git commands ever, no worktrees.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** sdd becomes a first-class citizen of coop: coop delivers the
skill, the skill reports run state to coop, the TUI shows a per-run
sub-row, and the arbiter's judge sees the run's declared manifest.

**Architecture:** the `/coop-sdd` skill text is embedded in the binary
and rewritten to `~/.claude/skills/coop-sdd/SKILL.md` on every hub
launch (the `hooks-settings.json` pattern). The skill calls a new
`coop sdd state|clear` verb (the `coop hook` contract: silent, exit 0,
best-effort) which writes `@coop_sdd_*` pane options; the poll reads
slug/task/phase through `paneFormat`, the judge reads the manifest with
one explicit `show -pv` per episode. Runs live under `.coop/sdd/<slug>/`
with the claim (`claim.md`, gitignored) split from the record (`run.md`,
tracked). Spec: `docs/superpowers/specs/2026-08-04-coop-sdd-design.md`.

**Tech Stack:** Go, tmux user options, `//go:embed`, Bubble Tea (existing).

## Global Constraints

- **Observe, never drive:** coop never reads sdd state back to sequence,
  gate, or dispatch anything in a run. No code path may violate this.
- `coop sdd` prints nothing and always exits 0, exactly like `coop hook`.
- The judge's manifest read is an explicit per-episode `PaneOption` call —
  the manifest never rides `paneFormat` (30 paths × every pane × 1s poll).
- All sdd state is untrusted where the judge or TUI consumes it: slug and
  paths go through `sanitizeNote` and render `%q` in the judge prompt.
- Fixture paths/names are always generic (`/home/user/sprocket-v2`,
  slug `2026-08-04-widget`) — never the developer's real paths (CLAUDE.md
  testing rules). Anything written goes under `t.TempDir()`.
- tmux ≤3.4 vis(3)-escapes `-F`/`show` output: any `\x1f`-joined value is
  split with `splitFields`, never `strings.Split` on the raw byte.
- Match surrounding comment density and idiom; best-effort tmux writes get
  a comment saying so.

```go
package hub

import (
	"fmt"
	"os"
	"path/filepath"
	"strings"
)

// SDD run state, published by the coop-sdd skill through `coop sdd`
// (cmd/coop/sddcli.go) onto its own pane. Reporting side-channel only:
// coop renders it and hands it to the judge as context, and never reads
// it back to drive the run — a silent skill still works, it just shows
// nothing. Untrusted like every pane option on this socket.
const (
	SDDSlugMarker  = "@coop_sdd_slug"  // run slug; presence = active run
	SDDTaskMarker  = "@coop_sdd_task"  // "3/7" during impl
	SDDPhaseMarker = "@coop_sdd_phase" // "setup" | "impl" | "review"
	// SDDManifestMarker is the declared file list, \x1f-joined. Read only
	// by the judge with an explicit show -pv once per episode — never in
	// paneFormat, where 30 paths per pane would ride every poll tick.
	SDDManifestMarker = "@coop_sdd_manifest"
	SDDRunMarker      = "@coop_sdd_run" // absolute path to run.md, for the human
)

// sddMarkers is every option the sdd side-channel manages. Slug first:
// the slug is what makes the sub-row exist, so a clear that fails
// halfway has already removed the row rather than leaving one with
// stale fields under it.
var sddMarkers = []string{
	SDDSlugMarker, SDDTaskMarker, SDDPhaseMarker, SDDManifestMarker, SDDRunMarker,
}

// sddManifestMax bounds the published path list. A manifest past it is
// truncated at publish — the judge's prompt says "… N more" from its own
// cap, so nothing downstream mistakes the bound for the whole.
const sddManifestMax = 200

// sddRunMax bounds the run.md read — a run file is a page of prose and a
// path list, so anything huge is not one.
const sddRunMax = 1 << 20

// SDDState is one publishable snapshot of a run. Every call carries the
// whole state so a missed call self-heals at the next one.
type SDDState struct {
	Slug     string
	Task     string // "3/7", "" outside impl
	Phase    string // "setup" | "impl" | "review", "" if unknown
	RunPath  string // absolute
	Manifest []string
}

// ParseManifest pulls the declared paths out of a run.md: the non-empty
// lines under "## Manifest" until the next heading, with an optional
// "- " bullet stripped. The format is a contract coop owns both ends of
// — the embedded skill writes it, this reads it.
func ParseManifest(content string) []string {
	var paths []string
	in := false
	for _, line := range strings.Split(content, "\n") {
		t := strings.TrimSpace(line)
		if strings.HasPrefix(t, "#") {
			in = t == "## Manifest"
			continue
		}
		if in && t != "" {
			paths = append(paths, strings.TrimPrefix(t, "- "))
		}
	}
	return paths
}

// LoadSDDState builds the publishable state from a run.md path plus the
// caller's flags. false for anything unusable — the CLI no-ops rather
// than publishing junk, the same direction every hook-path failure takes.
func LoadSDDState(runPath string, task, total int, phase string) (SDDState, bool) {
	abs, err := filepath.Abs(runPath)
	if err != nil {
		return SDDState{}, false
	}
	fi, err := os.Stat(abs)
	if err != nil || !fi.Mode().IsRegular() || fi.Size() > sddRunMax {
		return SDDState{}, false
	}
	raw, err := os.ReadFile(abs)
	if err != nil {
		return SDDState{}, false
	}
	slug := filepath.Base(filepath.Dir(abs))
	if slug == "." || slug == string(filepath.Separator) {
		return SDDState{}, false
	}
	st := SDDState{Slug: slug, RunPath: abs, Manifest: ParseManifest(string(raw))}
	if len(st.Manifest) > sddManifestMax {
		st.Manifest = st.Manifest[:sddManifestMax]
	}
	if task > 0 && total > 0 {
		st.Task = fmt.Sprintf("%d/%d", task, total)
	}
	switch phase {
	case "setup", "impl", "review":
		st.Phase = phase
	}
	return st, true
}

// ApplySDDState writes one snapshot onto the pane. An empty field unsets
// its option — whole-state semantics, so a phase change from impl to
// review retires the task fraction instead of stranding it. The slug is
// written last: it is what makes the sub-row appear, so a write that
// fails halfway shows nothing rather than a row with empty fields.
func ApplySDDState(tm Tmux, pane string, st SDDState) error {
	writes := []struct{ name, val string }{
		{SDDManifestMarker, strings.Join(st.Manifest, "\x1f")},
		{SDDRunMarker, st.RunPath},
		{SDDTaskMarker, st.Task},
		{SDDPhaseMarker, st.Phase},
		{SDDSlugMarker, st.Slug},
	}
	for _, w := range writes {
		if w.val == "" {
			if err := tm.UnsetPaneOption(pane, w.name); err != nil {
				return err
			}
			continue
		}
		if err := tm.SetPaneOption(pane, w.name, w.val); err != nil {
			return err
		}
	}
	return nil
}

// ClearSDDState retires the whole side-channel. Best-effort in the same
// shape as ApplyHook's SessionEnd loop: keep going past a failed unset
// and report the first error — a marker left behind self-heals when the
// pane dies.
func ClearSDDState(tm Tmux, pane string) error {
	var first error
	for _, m := range sddMarkers {
		if err := tm.UnsetPaneOption(pane, m); err != nil && first == nil {
			first = err
		}
	}
	return first
}
```

```go
package main

import (
	"flag"
	"io"

	"coop/internal/hub"
)

// isSDDCmd reports whether argv selects the sdd subcommand — the run
// state publisher the coop-sdd skill invokes at run boundaries.
func isSDDCmd(args []string) bool {
	return len(args) > 0 && args[0] == "sdd"
}

// runSDDCLI publishes sdd run state onto this pane's user options, or
// clears it. Same contract as coop hook, for the same reason: it runs
// inside a monitored session where stdout/stderr belong to that session,
// so it prints nothing and always exits 0 — a failure is one stale
// sub-row, corrected by the next call or the pane's death, never a
// wedged run. The state is a reporting side-channel: nothing in coop
// reads it back to drive the run.
func runSDDCLI(args []string, getenv func(string) string) int {
	pane := getenv("TMUX_PANE")
	tmuxEnv := getenv("TMUX")
	if pane == "" || tmuxEnv == "" || len(args) < 2 {
		return 0 // not in a tmux pane coop could mark, or nothing asked
	}
	// hookSocket, not cliSocket: like the hook, this runs inside the
	// exact pane it is about to mark, so the only right socket is the one
	// that pane lives on.
	tm := &hub.ExecTmux{Socket: hookSocket(tmuxEnv)}
	switch args[1] {
	case "clear":
		_ = hub.ClearSDDState(tm, pane)
	case "state":
		fs := flag.NewFlagSet("coop sdd state", flag.ContinueOnError)
		fs.SetOutput(io.Discard)
		run := fs.String("run", "", "path to the run's run.md")
		task := fs.Int("task", 0, "current task number (with -total)")
		total := fs.Int("total", 0, "total tasks in the plan")
		phase := fs.String("phase", "", "setup | impl | review")
		if err := fs.Parse(args[2:]); err != nil {
			return 0
		}
		st, ok := hub.LoadSDDState(*run, *task, *total, *phase)
		if !ok {
			return 0
		}
		_ = hub.ApplySDDState(tm, pane, st)
	}
	return 0
}
```

````markdown
# coop-sdd (Streamlined Subagent-Driven Development)

Execute a plan in the working tree with a fresh implementer subagent per
task and a single broad review at the end. No worktree, no branches, no
commits, and no dependence on git state — the run tracks its own files.
The human does all real git, afterward.

**Core principle:** the run owns a declared set of files and snapshots
their before-state, so the final review sees exactly the run's work even
while your partner has unrelated changes in the same tree. Fresh context
per task, verified tests as the per-task gate, one whole-run review at
the end.

Your partner works on several things at once in this tree. Files outside
the manifest are someone else's work in progress. Treat them as
untouchable.

## Reporting to coop

This skill is delivered by coop, the tmux hub, and reports run state to
it so the session's row shows the run and its progress. The publish is a
reporting side-channel: coop only displays it and hands it to its
arbiter as context — it never reads it back to drive the run, and
neither do you. Every call is best-effort: `coop sdd` is silent and
always exits 0. If the `coop` binary is missing, skip every publish and
continue — never block on one, never retry one in a loop.

The calls, verbatim (paths relative to the repo root):

- after Setup completes:
  `coop sdd state -run .coop/sdd/<slug>/run.md -phase setup`
- when dispatching task N of M (once per task or wave member):
  `coop sdd state -run .coop/sdd/<slug>/run.md -task N -total M -phase impl`
- when the final review starts:
  `coop sdd state -run .coop/sdd/<slug>/run.md -phase review`
- in Finishing, after deleting claim.md:
  `coop sdd clear`

## Setup

1. `<slug>` = plan filename without extension.
2. Read the plan once. Scan it for internal conflicts or anything a
   reviewer would flag as a defect that the plan explicitly mandates.
   During the same scan, for each task the plan does not give a file list
   or a covering test command, infer them. Raise everything found —
   defects AND inferred file sets AND inferred test commands — as ONE
   batched question to your human partner before task 1. A file set your
   partner confirms counts as declared.
3. Build the **manifest**: the union of every task's file set. Read every
   other `.coop/sdd/*/claim.md` — the presence of a claim.md is the
   claim, and its `## Manifest` section is what it claims. If a claim
   overlaps your manifest, STOP: name the slug, the overlapping paths,
   and that run's date, and ask your partner whether it is still active.
   A finished run deletes its own claim.md, so a surviving claim is
   either live or abandoned and only your partner can tell you which.
   Never clear another run's claim on your own judgement.
4. If `.coop/sdd/<slug>/` already exists, read it before writing anything:
   - **claim.md present** — an unfinished prior run of this plan. Ask
     your partner whether to resume or discard (see Resume below).
   - **run.md only, no claim.md** — a *finished* prior run of this plan.
     Say so, delete its stale `base/` and `review.md`, and start fresh:
     the new run overwrites run.md. Git history preserves the old record
     — that is why run.md is tracked.
   Separately: a `.sdd/` directory at the repo root, or a slug folder
   holding a `finished` marker, `land.patch`, `task-*-brief.md`, or a
   `worktrees/` sibling, is a leftover from an older version of this
   skill. Report it, offer to delete it, and never resume or interpret it.
5. Write `.coop/sdd/<slug>/claim.md` AND `.coop/sdd/<slug>/run.md`, each
   once, with a single Write, never edited afterward (run.md gets one
   appended section in Finishing, nothing else): the plan path, the
   date, and a `## Manifest` section listing one path per line. claim.md
   is the claim other runs see; run.md is the durable record your
   partner commits with the work. Ensure `.coop/sdd/.gitignore` exists
   containing exactly these three lines: `claim.md`, `base/`,
   `review.md`.
6. Snapshot the before-state — `mkdir -p .coop/sdd/<slug>/base`, then one
   `cp --parents <every manifest file that exists> .coop/sdd/<slug>/base/`.
   A manifest file that does not exist yet gets no snapshot; that absence
   is how "created by this run" is represented. Never read files into
   context just to copy them.
7. Use TaskCreate to make one native task per plan task, numbered to
   match the plan; TaskUpdate to in_progress when dispatching, completed
   when done. Native tasks are the source of truth for progress and
   survive compaction — after compaction, TaskList is your recovery map.
8. Smoke-check each task's covering test command once, now. A gate that
   cannot run at all is a plan defect — raise it in step 2's batched
   question.
9. Publish: `coop sdd state -run .coop/sdd/<slug>/run.md -phase setup`

**Resume.** Resuming an unfinished run (claim.md present, partner said
resume): recreate the native tasks from the plan and use the plan plus
the current tree to judge which are already done. Do NOT re-snapshot
`base/` — it is the run's original baseline and is still correct.
Publish the setup state, then continue from the first unfinished task.
Discarding: delete `.coop/sdd/<slug>/` and start over. Touch only this
slug's folder; siblings may belong to concurrent runs.

## Per task

1. Publish first: `coop sdd state -run .coop/sdd/<slug>/run.md -task N
   -total M -phase impl` (best-effort, then move on immediately).
2. Dispatch a fresh implementer subagent with:
   - one line on where this task fits in the project
   - the plan path and task number: "read task N — it is your requirements"
   - interfaces/decisions from earlier tasks the plan cannot know
   - `Files:` the exact paths this task may touch
   - `Covering tests:` the exact command that gates this task
   - these hard rules: **touch only your declared files. If the task
     turns out to need any other file, stop and return NEEDS_CONTEXT
     rather than editing it — every other file in this tree belongs to
     unrelated work in progress. No git write commands, ever (no
     add/commit/stash/checkout/reset), no worktrees, no branch changes.**
     Edit files in place.
   - the contract: return only STATUS (DONE / DONE_WITH_CONCERNS /
     NEEDS_CONTEXT / BLOCKED), the files touched, and a one-line test
     summary.
3. Use the cheapest model that fits: complete spec touching 1-2 files →
   cheap tier; multi-file integration → mid tier; judgment/design →
   capable tier. Always name the model in the dispatch.
4. On DONE, in this order:
   - **Manifest check.** Compare the returned files-touched against the
     declared set. A file outside it has no `base/` snapshot, so the
     final review would silently omit that change. Stop, report exactly
     which file, and ask before continuing.
   - **Gate check.** Re-run the covering test command yourself — cheap
     Bash, not a subagent. Self-reported green is not the gate; green you
     observed is. A failure goes back to the implementer.
   - TaskUpdate to completed, with files touched and any concerns in the
     task's notes. Do NOT dispatch a reviewer.
5. On NEEDS_CONTEXT / BLOCKED: supply context or escalate per the plan;
   never let a stuck implementer retry unchanged. On DONE_WITH_CONCERNS:
   read the concerns, fix correctness/scope issues before moving on, and
   record observations in the task's notes.

## Parallel waves

Tasks may run concurrently ONLY when the plan proves they can't collide.
When it can't prove it, serialize — that is always correct.

- Group tasks into waves using the plan's per-task file lists and
  Interfaces blocks: a wave is tasks with (a) no dependency on each
  other's outputs and (b) pairwise-disjoint declared file sets
  (partner-confirmed sets from Setup step 2 count as declared). A task
  with no declared or confirmed file set runs alone. Cap waves at 4.
- Tasks that touch shared artifacts — lockfiles, dependency manifests,
  generated code, repo-wide formatting or renames — always run alone.
- Dispatch a wave's implementers in one message (parallel tool calls).
- Wave members run only their own covering tests, not broad suites. After
  ALL members return, run the manifest check on each, then re-run the
  union of their covering tests serially. Only then TaskUpdate the wave's
  tasks.
- If two wave members report the same file, treat the wave as suspect: if
  the combined tests pass, note it for the final reviewer; if they fail,
  redo those tasks serially from the current tree state.

## Final review (once, after all tasks)

1. Publish: `coop sdd state -run .coop/sdd/<slug>/run.md -phase review`
2. Build the review package into `.coop/sdd/<slug>/review.md`. This is
   the whole reason `base/` exists, and it is what keeps the review
   correct despite unrelated changes in the tree:
   - each manifest file with a snapshot:
     `diff -u .coop/sdd/<slug>/base/<path> <path>`
   - each manifest file without one (created by this run): its full
     current contents
   - skip binaries
   Never use `git diff` for this — it folds in your partner's concurrent
   work and buries the run's changes in it.
3. Dispatch one reviewer subagent on a capable model, read-only, with the
   review package, the plan path, and the concerns collected in the
   tasks' notes. It reports findings with file:line evidence,
   severity-rated.
4. Dispatch ONE fix subagent with the complete Critical/Important
   findings list — not one per finding. It is bound by the same manifest
   and re-runs the covering tests. Re-review only if the fixes were
   substantial.

## Finishing

1. There is no landing step. The edits have been in the working tree
   since task 1, and every gate already ran against the real tree.
2. Delete `.coop/sdd/<slug>/claim.md` and nothing else. That releases
   the manifest so another run may claim those files. Then append one
   `## Outcome` section to run.md — the date, what changed in a
   sentence, the review's verdict in a sentence, and test status. run.md
   stays: it is the record your partner commits with the work. `base/`
   and `review.md` also stay on disk deliberately: your partner reviews
   and commits after you stop, and those are what let them re-read
   exactly what the run changed without untangling it from their
   concurrent work.
3. Publish: `coop sdd clear`
4. Report to your human partner: the manifest, so they know exactly which
   paths this run touched; what changed; what the review found; and test
   status. **Never commit — they handle git themselves.** Stop.

Abandoning a run is your partner's call and their command — the manifest
in your report is what tells them which paths to revert. Do not offer to
revert files yourself.

## Red flags

- Creating a worktree, a branch, or a commit → none of those belong here.
- ANY git write command → your partner does all git. Read-only git isn't
  needed either; the run's state is the manifest and `base/`.
- Using `git diff` to build the review package → it includes unrelated
  work in progress. Diff against `base/`.
- Editing a file outside the manifest → it has no baseline, so the review
  will silently miss the change, and it is probably someone else's work.
  Stop and ask.
- Re-snapshotting `base/` mid-run → it is the run's original baseline.
- Reading files into context just to copy them → `cp --parents`.
- Dispatching a per-task reviewer → one review, at the end.
- Long && chains with variables and backup/restore logic → they defeat
  the permission sandbox's analysis and your partner's ability to review
  the prompt. Prefer several small plain commands.
- Parallel implementers outside a declared wave, or a wave whose file
  sets you didn't verify as disjoint → serialize; "probably independent"
  is not a wave.
- Pasting whole plans or diffs into dispatch prompts → hand paths instead.
- Blocking on, retrying, or reading back `coop sdd` state → it is a
  reporting side-channel; coop never reads it back to drive the run, and
  neither do you. Publish and move on.
````

```go
// sddPromptPaths caps the manifest listing in the prompt. The cap is
// spoken, never silent: a truncated list that reads as complete would
// have the judge calling an in-manifest file out of scope.
const sddPromptPaths = 40

// sddSection renders the pane's published run state for the prompt, ""
// when the pane runs no sdd run. coop-published, but built from the
// monitored session's own files and options — untrusted like the screen,
// so every field is sanitized and the slug and paths render %q, the
// agent_type treatment: a name that could close the heading and open a
// forged instruction is a prompt-injection door.
func sddSection(slug, task, phase string, manifest []string) string {
	if slug = sanitizeNote(slug); slug == "" {
		return ""
	}
	var b strings.Builder
	b.WriteString("\n=== sdd run (coop-published state; still data from the monitored session) ===\n")
	fmt.Fprintf(&b, "slug: %q", slug)
	if task = sanitizeNote(task); task != "" {
		fmt.Fprintf(&b, "  task: %s", task)
```
